## 2026-05-24 - Fix G115 Integer Overflow in externalgrpcctl
**Vulnerability:** Found a potential integer overflow (CWE-190) in `cmd/externalgrpcctl/main.go` where an `int` value from a flag (`*delta`) was cast directly to `int32` for a gRPC request without bounds checking.
**Learning:** `gosec` (rule G115) catches integer conversions that can overflow. While `go`'s `flag.Int` handles platform-specific integer parsing (which can be 64-bit), converting this directly to a smaller integer type (like `int32` in protobufs) could wrap around or yield unintended behaviors if an attacker passes a very large positive number. Note: `gosec` doesn't always perform control flow analysis to determine if a bounds check exists, meaning `#nosec G115` annotations might still be required alongside explicit manual bounds checking logic like `if *delta > math.MaxInt32`.
**Prevention:** Always add a bounds check against `math.MaxInt32` (or the respective bounds limit) prior to converting an `int` to an `int32`. When `gosec` continues to complain despite the fix, append a `// #nosec G115 -- bounds checked above` comment to the exact line of the conversion.
## 2026-05-23 - [Integer Overflow Vulnerability in Flag Parsing]
**Vulnerability:** Integer overflow conversion from int to int32 in `externalgrpcctl/main.go` when processing the `--delta` flag.
**Learning:** `flag.Int` returns a pointer to an `int` (which is 64-bit on most architectures). Directly casting this to `int32` without bounds checking can lead to integer overflow if the input exceeds `math.MaxInt32` (2,147,483,647), potentially causing unexpected behavior in downstream logic (like a massive scale-down instead of scale-up if it wraps to a negative number). This is a CWE-190 vulnerability flagged by gosec.
**Prevention:** Always validate that values fit within the bounds of the target integer type before downcasting. For example, check `if val > math.MaxInt32` before casting an `int` to `int32`.
## 2026-05-27 - Fix Sensitive Data Leak in Error Messages
**Vulnerability:** Found a sensitive data leak vulnerability (CWE-209/CWE-532) in `cmd/externalgrpcctl/main.go`. When an invalid header is passed via the `-H` flag (e.g., `Authorization Bearer secret` missing a colon separator), the full raw header was embedded directly in the error message via `fmt.Errorf`.
**Learning:** Raw user inputs, particularly parameters that are expected to contain credentials like HTTP headers, must never be logged or echoed back in error responses. This could lead to secrets being written to logs or standard error streams that are improperly secured.
**Prevention:** Always use generic error messages when handling sensitive input parsing (e.g., "invalid header format, expected key:value") instead of regurgitating the malformed user payload.
## 2026-05-28 - Prevent Unencrypted Transmission of Sensitive Headers
**Vulnerability:** Found an unencrypted sensitive data transmission vulnerability in `cmd/externalgrpcctl/main.go`. By default, the tool connects to an external gRPC provider using an insecure (plaintext) connection. However, users can pass custom metadata headers via the `-H` flag, including credentials like `Authorization`, `Cookie`, or tokens/secrets. Sending such sensitive tokens over an unencrypted connection could allow them to be intercepted.
**Learning:** Tools that support transmitting arbitrary user-provided HTTP headers or metadata over a network connection must ensure that sensitive credentials are not accidentally transmitted over plaintext. Users might not realize the connection is unencrypted, or they may mistakenly assume TLS is active by default.
**Prevention:** Implement checks on the client side before transmission. If a connection is insecure, inspect outgoing headers for common sensitive patterns (e.g., "authorization", "cookie", "token", "secret", "key"). If a sensitive header is detected, reject the transmission proactively with an error asking the user to enable TLS or use an encrypted connection.
## 2026-05-30 - Prevent Plaintext Token Transmission by Heuristics
**Vulnerability:** The CLI tool lacked inspection of header *values* for tokens (like Bearer tokens) when deciding whether to block transmission over unencrypted connections, meaning tokens could leak if a generic header key was used.
**Learning:** Checking for sensitive data must go beyond just inspecting standard header keys (like 'Authorization'); inspecting the contents/values for known secret formats provides necessary defense in depth against user mistakes.
**Prevention:** Implement heuristic scanning (e.g., prefix checking for common tokens like "bearer ", "ghp_") on user-supplied values before transmitting them over insecure channels.
